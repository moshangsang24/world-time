### P0-1 太阳直射点经度计算错误（核心功能）

- [x] 已修复（2026-11-12）：直射点经度改为由 UTC 时刻和均时差计算，测试对照 SunCalc，高度角误差 < 0.3°

**位置**：`src/utils/sunCalculations.ts:40`

```ts
const longitude = this.normalizeLongitude(sunTrueLong + 180);
```

**现象**：`sunTrueLong` 是太阳黄经（一年走 360°），不是地理经度。公式缺少地球自转项（GMST/时角），算出的“太阳经度”一天内几乎不动，只随季节缓慢漂移。

实测对比（本实现 vs 应有直射点经度）：

| 时刻 | 本实现 `longitude` | 正确值 |
|---|---|---|
| 2025-06-21T12:00Z | -89.6° | ≈ 0° |
| 2025-03-20T12:00Z | -179.9° | ≈ 0° |
| 2025-12-21T12:00Z | +89.9° | ≈ 0° |
| 2025-10-22T04:00Z | +29.0° | ≈ +120°E |

**影响**：

- `isDaylight()`（`sunCalculations.ts:111-117`）城市昼夜判断大面积错误。实测 2025-06-21T04:00Z：北京应为白天（高度角 73.2°），当前判为夜晚（-22.1°）；纽约应为夜晚，当前判为白天。
- `WorldMap2D` 的昼夜色带、城市日/夜颜色、`CityTimeCard` 的太阳/月亮图标全部继承该错误。
- `calculateDayNightBoundary()` 的晨昏线被整体旋转到错误经度。

**修复建议**：

```
GMST(deg) = 280.46061837 + 360.98564736629 * (JD - 2451545)
λ_subsolar = normalize(RA - GMST)   // 归一化到 [-180, 180]
```

最小改动可用 `longitude = normalize(-hourAngle)`（当前 `hourAngle ≈ 15 * (UTC - 12)`，与该式近似）。更稳妥的是直接使用 `SunCalc.getPosition(date, lat, lng)`，注意它返回**弧度**，需乘 `180 / Math.PI`。赤纬 `declination` 当前计算是正确的，不需要改。

### P1-4 晨昏线在春/秋分附近退化

- [x] 已修复（2026-11-12）：改用 `atan` 并对极小赤纬做钳制，春秋分测试通过

**位置**：`src/utils/sunCalculations.ts:58-86`

**现象**：`calculateDayNightBoundary()` 按经度采样求纬度（`lat = atan2(-cosH, tanδ)`）。当赤纬 δ→0 时，晨昏线退化为两条经线，无法表示成 `lat(lng)` 单值函数：δ=0 时全部点落在极点，δ=1° 时 171/181 个点 `|lat| > 80°`。

**修复建议**：改为按纬度参数化（对每个 φ 求 `H = ±acos(-tanφ·tanδ)`），或直接对太阳位置采样生成闭合曲线。

### P1-5 3D 经纬度逆变换对正东经错误

- [x] 已修复（2026-11-12）：`vector3ToLatLng` 与 `cartesianToLatLng` 已改为角度归一化，并有往返测试。下文 `SunlightShader` / `screenToSphere` 的符号问题仍在（3D 未接线，暂不处理）

**位置**：`src/utils/coordinateUtils.ts:33-44`（`vector3ToLatLng`）、`src/utils/sunCalculations.ts:236`（同名实现）

**现象**：

```ts
const longitude = Math.atan2(z, -x) * RAD_TO_DEG - 180;
```

`atan2` 返回 `(-180, 180]`，减 180 后落到 `(-360, 0]`，再 `clamp(-180, 180)`。结果只有西经可逆：

| 输入 | 反算 |
|---|---|
| (0, 0) | 0 ✓ |
| (0, 20) | -340 → clamp **-180** ✗ |
| (0, 90) | -270 → **-180** ✗ |
| (39.9, 116.4) | -243.6 → **-180** ✗ |

**修复**：不要 clamp，做角度归一化：`normalizeAngle(atan2(z, -x) * 180/PI - 180)`。

同时注意：`SunlightShader.tsx:76-86` 构造太阳方向时 x 符号与 `latLngToVector3` 相反（地球/城市是 `-x`，太阳是 `+x`），接上 3D 后会错位；`screenToSphere()` 也使用 `+x`，且没有相机朝向/宽高比处理，当前无调用，不要使用。

### P2-1 性能问题

- [ ] 部分修复（2026-11-12）：底图已缓存到离屏 canvas；`useScrollControl` 不再重绑监听；`useSunPosition` 去掉了无用计算并改用 selector。其余组件的整 store 订阅仍未改

- 所有 `useTimeStore()` / `useTimeState()` 都是整 store 订阅，实时模式下每秒触发所有消费组件重渲染；应改用 selector。
- `WorldMap2D` 每秒全量重绘整个 canvas（依赖 `cities` 新数组），没有 `requestAnimationFrame`、离屏 canvas 或缓存。
- `useSunPosition` 每次 tick 被重复调用 2–3 次（`EarthVisualization` → `useTimeState` → `useSunPosition`，`WorldMap2D` 又单独调用），且急切计算无人使用的 `calculateSunlightData` / `calculateDayNightBoundary`（后者内部还会再调 suncalc）。
- `useScrollControl` 的 effect 依赖 `timeOffset`，每滚一次就解绑/重绑 document 监听；handler 闭包里的 `timeOffset` 同一帧内可能读到旧值，快速滚动会丢步。建议用 `useTimeStore.getState().timeOffset`。
